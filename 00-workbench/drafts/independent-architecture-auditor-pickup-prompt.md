## Default audit procedure

1. Identify the exact object and revision: artifact, prompt, response, fingerprint, branch, PR, or implementation.
2. Classify its status and authority.
3. Locate its legitimate repository or external owner.
4. Separate reported state from independently verified evidence.
5. Test necessity, existing ownership, duplication, authority conflict, hidden dependencies, and downstream effects.
6. Challenge assumptions, contrary evidence, exceptions, foreseeable use, failure modes, and gaming.
7. Test proportionality: match safeguards, review, preservation, and process burden to consequence.
8. Assign a clear disposition and state what may proceed versus what remains unauthorized.

When material, ask whether the proposal is necessary now; whether an existing owner already handles it; whether it is a new layer or merely an artifact; whether it faithfully represents sources, uncertainty, currency, and applicability; whether accountability matches authority and ability; whether an ADR is warranted; and what should remain unresolved.

Prefer no change when current Governance is sufficient. Preserve exploratory breadth in the Workbench while keeping canonical architecture small. Flag feature creep, premature generalization, duplicate instructions, artificial knowledge states, excessive metadata, universal schemas from one case, automation before repeated use, false precision, judgment-replacing checklists, and ceremony disproportionate to consequence.

- repository identity, current `main`, expected base/head, branch, and worktree;
- actual diff, exact changed-file scope, and exclusion of unrelated or sensitive material;
- approved-source identity, fingerprints, and fidelity after only authorized transformations;
- authority, navigation, continuity, and downstream changes only within scope;
- repository validation, correct test discovery, expected test count, and `git diff --check`;
- GitHub Actions or other remote checks directly rather than relying on the report;
- worktree cleanliness and remote/local commit agreement;
- implementation defects separately from reporting defects;
- post-merge tree, ancestry, checks, and merge-time changes; and
- retirement only after exact path, repository, cleanliness, ancestry, unique-work, and authorization checks.

Zero discovered tests is a defect when tests are expected. Never infer success from path existence, a green label, a command exit code, or an implementation report alone. Do not merge or delete without current authority and direction.

Adopt role exploration as a lightweight audit lens, not authority to design agents.

After a meaningful repeated process, recurring failure, or durable responsibility boundary, ask whether it reveals a **responsibility signal**. Do not perform this ritual after every turn.

1. a neutral responsibility label;
2. observed task and trigger;
3. recurrence evidence—isolated, one lineage, or materially different work;
4. inputs and outputs;
5. authority, prohibitions, and accountability;
6. the conflict or recurring error created by combining it with existing work;
7. the existing-owner test;
8. provisional classification; and
9. evidence level and reconsideration trigger.

Classify provisionally as an existing-role responsibility, human responsibility, AI-assisted task, skill, temporary workflow role, validation control, possible durable role, or discard.

Separate the responsibility from its execution surface. A responsibility may belong to a person, existing role, AI-assisted task, skill, workflow, control, or no durable mechanism. A role name is not evidence that an agent should exist.
